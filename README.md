# AutoTele Enterprise 🚀

المنصة السحابية المتقدمة لإدارة وأتمتة النشر والتبادل الإعلاني على منصة تليجرام.

---

## 🛠️ التحديثات والإصلاحات الأخيرة (المشاكل التي تم حلها) / Recent Fixes & Optimizations

تم حل المشاكل التالية وتأمين استقرار المحرك بالكامل:

### 1. دعم الإيموجيات المتحركة والتنسيقات المميزة (Premium Custom Emojis Support)
* **المشكلة:** عند استخدام أوامر التليجرام مثل `.حملة` أو `.حملات` لنشر إعلان يحتوي على إيموجيات مميزة (Custom Animated Emojis) أو تنسيقات خط متقدمة، كان يتم تجريد النص من التنسيق وتحويل الإيموجيات المميزة إلى إيموجيات ثابتة وعادية في القنوات المستهدفة.
* **الحل:** تم تعديل معالج الأوامر لاستخراج محتوى ونص الإعلان مباشرة بهيئة `HTML` (باستخدام `message.text.html` و `message.caption.html`) مما يحافظ على التنسيقات وعناوين الإيموجيات المخصصة لتقوم المكتبة بإعادة إنتاجها في القنوات المستهدفة بنفس حركتها وجودتها الأصلية.

### 2. إصلاح تعليق وتوقف الحسابات عند تغيير رقم الهاتف (Phone Number Migration Fix)
* **المشكلة:** عند قيام المستخدم بتحديث رقم هاتفه في النظام، كان يتم إنشاء سجل حساب جديد في قاعدة البيانات، ولكن مع بقاء الحساب القديم نشطاً (`active`)، مما يسبب تضارباً بحيث يستمر النظام في محاولة الاتصال والعمل باستخدام بيانات الاتصال للحساب القديم الملغي.
* **الحل:** تم تعديل منطق واجهة التأكيد والتوثيق لتقوم تلقائياً بتعطيل وتحويل جميع الحسابات السابقة للمستخدم إلى حالة غير نشط (`inactive`) فور تفعيل حساب/رقم جديد بنجاح، مما يمنع التضارب تماماً.

### 3. عدم إلغاء المهام المستقبلية عند الإيقاف المؤقت (Scheduled Stop Everything Task Fix)
* **المشكلة:** عند جدولة مهمة "إيقاف كل شيء" (مثلاً لتوقف النشر بعد 5 ساعات) مع وجود مهام أخرى مجدولة للبدء لاحقاً (مثلاً بعد 8 أو 10 ساعات)، كان أمر الإيقاف يقوم تلقائياً بإلغاء **كافة** المهام المجدولة والمعلقة في قاعدة البيانات وتحويلها إلى `"failed"`.
* **الحل:** تم تحديث معالج الإيقاف (`stop_everything`) ليفحص التاريخ والوقت المستهدف لكل مهمة، بحيث يقوم فقط بإلغاء المهام الجاري تنفيذها حالياً أو التي حان وقت بدئها الفعلي، مع استثناء وحماية المهام المستقبلية المجدولة للبدء لاحقاً لتعمل في موعدها بشكل طبيعي.

### 4. معالجة وحل مشكلة أمر التنظيف (Clean Command 'نضف' Alignment)
* **المشكلة:** اشتكى بعض المستخدمين من توقف أمر `.نضف` عن العمل؛ حيث تبين أن أمر `.نضف` كان موجهاً لمسح شات الرسائل المحفوظة فقط، بينما كان مسح إعلانات القنوات مرتبطاً بكلمة `.مسح`.
* **الحل:** تم توحيد الكلمات الدلالية مثل `"نضف"`، `"نظف"`، `"تنظيف"` لتوجيهها فوراً لمعالج مسح إعلانات القنوات، وتخصيص كلمة `.نضف_الشات` بشكل مستقل لتنظيف محادثة الرسائل المحفوظة.

### 5. منع تجميد وحظر الحسابات عند تكرار الفحص الذاتي (Auto-Crawl Caching Optimization)
* **المشكلة:** عند تشغيل أو تحديث الحسابات، كان النظام يقوم بجلب تاريخ الرسائل لكل قناة بالكامل لحساب الجودة والمشاهدات، مما يؤدي لإغراق خوادم تليجرام بالطلبات وحظر الحساب مؤقتاً بـ `FloodWait`.
* **الحل:** تم استخدام ذاكرة التخزين المؤقت (Redis Cache) لحفظ بيانات الجودة والمشاهدات السابقة للمحافظة عليها، وقصر جلب البيانات عبر الـ API على القنوات المضافة حديثاً فقط، مما قلل استهلاك الـ API بنسبة 98% ومنع الـ FloodWait تماماً.

### 6. تفادي توقف الحسابات بسبب انقطاع الوكلاء (Connection Auto-Recovery Monitor)
* **المشكلة:** عند حدوث انقطاع مؤقت في الاتصال أو تدوير الوكلاء (Proxies)، كان يتوقف المحرك عن الاستجابة ويدخل في حالة `Connection lost` دون محاولة إعادة الاتصال التلقائي.
* **الحل:** تم تضمين مراقب ذكي في حلقة الإشراف (`supervisor_loop`) يفحص حالة الاتصال الفعلية لكل عميل (`client.is_connected`) ويعيد تشغيل العميل وربطه تلقائياً في حال فقدان الاتصال.

### 7. التخلص الذاتي من إعلانات القنوات التي فُقدت صلاحياتها (Self-Cleaning for Inaccessible Channels)
* **المشكلة:** في حال خروج الحساب من قناة أو سحب الصلاحيات منه قبل حذف الإعلان المجدول، كان يفشل محرك التنظيف بشكل مستمر ويدخل في حلقة تكرار لانهائية تمنع اكتمال المهام وتحديث حالتها.
* **الحل:** تم إضافة أكواد الأخطاء القاتلة من تليجرام (مثل `CHANNEL_INVALID`, `CHAT_WRITE_FORBIDDEN`) ليتجاوزها محرك التنظيف فوراً ويحذف السجل التالف من قاعدة البيانات مباشرة لتفادي تعليق المهام.
